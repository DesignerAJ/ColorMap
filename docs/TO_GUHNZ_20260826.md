## Merge 방식에 대하여
머지 방식의 변경은 반대.  
AI는 하루에도 수십 개씩 커밋을 할 수 있기 때문에 main 브랜치에 많은 양의 커밋을 남기는 것은 유지보수와 깔끔한 관리를 위해선 옳지 않다고 생각.

건수가 원하는  
작업 기록을 남겨 AI가 참고하게 하려면 두 가지 방법이 있음.
1. dev 브랜치들의 커밋과 작업 기록을 참고하게 하면됨. (안정화 확인하고 브랜치 삭제해도 된다 판단될 때 까지는 삭제 안함)
2. 커밋과 별개로 docs 폴더에 'DEV Log_GUHNZ.md' 등으로 커밋이나 주요 작업 내용을 AI가 기록하게 해두고 필요시 참고하게하는 것도 방법. (생성해둠)

## 버전 표기에 대하여
이번 배포 버전을 v3.1.0으로 정의 하며, 버전표기법은 아래와 같음. (README.md 문서에도 간단하게 삽입해둠)

**버전표기법**
v(Major.Minor.Patch)

**Major**
-하위 버전과 호환되지 않는 변화가 생겼을 때
-대대적인 변화가 일어났을 때
-클라이언트가 1.0.0 버전의 API 접근 방식으로 2.0.0 버전에 접속할 수 없을 때

**Minor**
-하위 버전과 호환이 되면서, 새로운 기능이 추가 될 때
-새로운 기능이 추가된 API 가 나왔지만, 기존의 공개된 API 가 하위 호환되고 있을 때
-기존의 기능이 변경되거나 사용 방법이 변경 되었을 때

**Patch**
-버그 수정
-기존 클라이언트가 알아차리지 못할 정도의 작은 변화가 있을 때
-서버 코드 내부적으로 소스가 수정되었을 때
-당연한 얘기겠지만, 이 모든 것들이 하위 버전과 호환될 때
